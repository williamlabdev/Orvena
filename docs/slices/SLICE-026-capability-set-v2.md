# Slice: capability set v2 —— 尺飽和了,得換一把

> 狀態:**定案(0806,william 裁)**——DRAFT 期的四項 0806 裁決全數落地後
> 轉定案,`capability-v2.yaml` 據此動工。同裁決定了校準規模:**兩格都跑、
> repeat 皆 n=3**(死法分類 n=3 已飽和是實測;通過率本來就不是校準值),
> 同取樣、分批單趟 ≤10 run。envelope 檢查表仍是推的:凍題前逐題真跑補量照舊。
> 起因:native 0.4.0(slice-025)之後,矩陣四格全滿——
> native {14b 100%, 35b 100%} vs aider {96%, 96%}。0% 耗盡、mean 2.2 步。
> 現行 set 已經量不出任何後續 loop 投資的差別,再做刀也只是在 100% 上原地踏步。

## 這把新尺要量什麼(不是「更難」,是「還沒飽和的維度」)

現行 set 的四個鑑別維度(preservation / anchored-edit / localization /
convergence)在 14b 上全部到頂。但 slice-025 的驗屍暴露了一件事:
**其中一個維度是被洗掉的,不是被解決的**——`cap-locate-broken-ref` 現在
一步完賽,靠的是檔名 `install.md` 自己說出了內容,模型從未查證。
所以 v2 的第一條設計條件不是加難度,是**把「查證」這個維度救回來**。

四個候選維度,依「現行 set 量不到」排序:

1. **查證(verification)**——答案不能從檔名推得,必須讀過內容才知道是哪一個。
2. **枚舉(enumeration)**——一處改動牽動多處引用,要的是「找齊」而非「找到」。
3. **多跳證據(multi-hop)**——證據 A 指向 B,B 才有值。現行 audit-services
   只有一跳,slice-023 之後就變送分題。
4. **狀態重讀(re-reading)**——修 A 會改變 B 的狀況,照計畫重播的迴圈會失敗。

## 設計條件(v1 的誠實規則全部繼承,加兩條)

繼承 `benchmarks/capability.yaml` 檔頭的四條(`tests/` 唯讀、不給額外唯讀命令、
不用 toolchain、seed 50 行內),外加:

5. **沒有一題可以只靠 inventory 解掉**。每題的答案都必須至少經過一次
   READ/SEARCH,且其目標**無法從檔名推斷**。這是 slice-025 的直接教訓:
   給了地圖之後,「檔名即答案」的題目就不再量能力,只量識字。
6. **不得混入 temptation**(v1 既有規則的重申,但 v2 更容易犯)。
   inventory 讓模型看見可寫清單以外的檔,「該不該碰鄰居」的題目現在寫起來
   很順手——那是 compliance,寫進來就會讓一個數字同時量兩件事。
   v2 的做法見下方規則 7——**唯讀語料 + 一個小的可寫目標**。
   (本條原本寫的是「把候選檔全部設為 writable」,已被 0805 的探針否證:
   writable 的內容會整份進 prompt,那等於把答案送出去。)

(規則 **7 與 8** 是 0805 探針推翻設計前提之後補的,寫在下方
「探針第一跑」那節,不在這裡——編號連續,位置不連續。)

9. **每一題都必須在 8 個工具動作內可解**(0806 裁,見末節)。`MAX_STEPS` 是
   `crates/orvena-core/src/benchmark/runner.rs:36` 的**寫死常數 8**,專案
   `.orvena/orvena.yaml` 的 `max_steps:` **到不了 bench runner**(實測:
   改成 16 後 blocker 仍印 `max_steps (8)`)。它的 doc comment 明說改值即換
   envelope、跨值不可 pool。所以這不是可調參數,是**尺的一部分**。

   **一步 ≠ 一個動作**(0806 更正,查 `agent/driver.rs`):
   `driver.rs:115` 的 `for step_no in 1..=max_steps` 一步是**一次模型呼叫**,
   而 `driver.rs:160-162` 每次呼叫解析出的 actions 是**沒有上限的 Vec**。
   8 步限的是**回合數**(觀察→行動的次數),不是工作量——實測有一趟
   `steps=2 / read=13 / tool_calls=14`,13 個檔在兩次呼叫內讀完。

   所以造題時要算的是**最壞情況**:一個不批次的模型,一步一動作,
   總共只有 **8 個工具動作**。題目的最短解法路徑(含最後那次 write)
   必須 **≤8 個動作**,否則不批次的模型連寫答案都到不了——
   而「會不會批次」是策略,不是能力(下一節的 30 run)。

### 一個建議:toolchain 仍然不進 v2

SLICE-024 遺留的候選 B 寫的是「多檔跨檔、真 toolchain」。前半照收,
**後半建議否決**:編譯時間會節流 convergence 題(v1 規則 3 的原意),
而且讀數會變成機器規格的函數,跨機不可比。難度應該來自資訊結構,
不是來自等 cargo。若你要保留這條路,它該是**另一把尺**(engineering
realism set),不是 capability 的 v2——兩者的可比鍵與跑法都不同。

### 逐題的 envelope 檢查(0806,設計條件 9 的第一道關)

判準有兩欄,兩欄都要過:**動作數**(不批次的最壞情況,含最後那次 write,
額度 8)與**回合數**(有序依賴逼出來的最少模型呼叫,額度 8)。
兩者是不同的資源——C/F/H 吃回合,A/G 吃動作。

⚠️ 下表是**從題目描述推的,不是量的**。凍題前每一題都要用真跑對一次。

| # | 最短路徑(動作) | 最少回合 | 判定 |
|---|---|---|---|
| A | READ×4 + EDIT = **5** | 1 | ✅ 且有第二條路(SEARCH×1 + EDIT = 2),兩條都在額度內 |
| B | EDIT×3 = **3** | 1 | ✅ 最寬鬆。三檔 writable 故內容已在 prompt,不需 READ |
| C | EDIT×2 = **2** | **2** | ✅ 吃的是回合不是動作;唯一真正需要多回合的題,設計正確 |
| D | READ×2 + WRITE = **3** | 1 | ⚠️ 真跑否證了這行的隱含假設,見「D/E 重讀迴圈定性」 |
| E | READ×2 + WRITE = **3** | 1 | ⚠️ 同 D;防繞過機制已改,見下 |
| F | EDIT×3 = **3** | **3** | ✅ 兩次 ambiguous 各要一個回合收 gate 回饋 |
| G | READ×5 + WRITE = **6** | 1 | ✅(已縮檔;12 檔版是 13 個動作,超額) |
| H | READ×3 + EDIT×3 = **6** | **3** | ✅ 已降為 3 個缺陷,見下 |

**已量(0806,35b 單趟 envelope 真跑;batch1 = A–G,batch2 = H–M)**:
13 題全數真跑過一輪(engineering、native 0.4.0、校準取樣、repeat 1;
報表 `bench-runs/20260806-capv2-envelope-batch{1,2}-qwen3-6-35b.json`)。
結果:10/13 過;死的三題 D/E/K 全是多跳家族、同一死法(見下節定性)。
步數注記:M(4 缺陷)**壓線 8 步過**——零餘裕的預測準確,天花板側備用的
定位成立;H 改 3 缺陷後未在本輪出事。單趟是 envelope 驗證,不是校準值;
n=3 的死法表仍以出廠校準跑為準。

**H 原本是唯一沒過的,已改**(0806 裁:≥4 → 3 個缺陷)。原版每輪先 READ 再 EDIT
剛好用滿 8 個動作,任何一次多讀、多搜或一次修錯都直接出局——而那些正是失敗 run
的常態。零餘裕會讓它變成 G 的翻版:批次的模型過、不批次的模型連做完都不可能。
3 個缺陷是動作 6、回合 3,留一格餘裕,而**依賴層保留**(其中一個要修完前一個才浮現),
所以它與備用題 L 的差別仍在。**原版(4 缺陷)留作天花板側備用 M**。

沒有走「讓 check 回饋帶足定位資訊、省掉每輪的 READ」那條:它動作數會降到 4,
但代價是把定位那一半送掉,題目只剩「會不會逐輪收斂」。

**E 的防繞過換了機制**(0806 裁)。E 原本靠「一跳解不掉」立題,但暴力路徑
(不讀 index、把數份 data 檔全讀)只要 data 檔 ≤6 就在動作額度內——多跳維度被繞過。
**沒有用「把 data 檔加到讀不完」去擋**:那是 G 踩過的坑,擋掉的是不批次的模型,
不是繞過的行為。改成資訊結構——數份 data 檔的值**外觀無從分辨**
(格式相同、都像合法答案),不讀 index 就算全讀完也選不出來。
暴力路徑仍然跑得完,只是跑完仍不知道答案。**這才是「必須多跳」,
而不是「沒空間繞過」**;預算擋出來的必要性是假的,資訊結構擋出來的才是真的。
K 同理照改。

### D/E 重讀迴圈定性:視窗一步深 + 接地規則 = 結構性死鎖(0806,真跑 transcript)

35b envelope 真跑(batch1)裡 D/E 同死:8–9 READ、零 write 零 search、燒滿 8 步。
n=1 未定性,單題重跑取證(同 batch1 條件:engineering、native、校準取樣、repeat 1;
driver 無逐步紀錄,在 runner 與 ollama 之間掛記錄 proxy 截整包)。兩題都重現原死法,
transcript 與報表在 `bench-runs/20260806-probe-de-reread-*`。

**死法逐字**:D 是 READ registry → READ site-b → READ registry → …交替到死;
E 同型(index ↔ amber.dat)。模型第 1–2 步就找對了目標——這不是迷路。

**機制,三件事相加**:

1. native loop 是無狀態重渲染:每步 prompt = system + task + writable 檔現況
   + **上一步**的工具證據。`prior_evidence` 是覆寫不是累積(driver.rs 步尾
   `prior_evidence = format!("{tool_evidence}{evidence}")`)——
   **證據視窗恰好一步深,是建構性質**。
2. D/E 的 write 需要兩份證據同時在場(哪個目標是 active/current + 該目標的值),
   分居兩檔。串行單動作策略下,視窗永遠只裝得下一半。
3. system prompt 的接地規則(「不得寫沒親眼見過的值,先 READ/SEARCH」)對
   無狀態重渲染的模型而言,「記得」與「捏造」無從分辨——上上步讀過、
   現在不在眼前,就等於沒讀過。所以它回頭重讀缺的那半,同時把另一半擠出視窗。

**定性:行為發現,不是題目缺陷。** 題目在額度內可解,但解路只有兩條:
(a) **批次**——一步內連發多個 READ,同一步的 tool_evidence 在視窗內共存,
下一步兩份證據都在場(動作 5、回合 2);(b) **SEARCH 打包**——一次跨檔
SEARCH 的 hits 天生同窗(動作 2、回合 2)。35b 兩跑 search=0、每步單動作,
一條都沒走。

**對上表 D/E 行的修正**:「動作 3、回合 1」是紙上推的,且隱含「證據會累積」
的假設。真跑下:串行 READ 路徑**任何預算都解不掉**——不是超額,是不終止;
回合下限是 2,不是 1。設計條件 9 的「no honest path may exceed budget」在
D/E 上要補一句:誠實的串行路徑不是超額,是**不存在**。

**第二批真跑追認:K 同死同型**(0806,batch2)。K(E 的同維度加難版)
在 `index.txt` ↔ `east.dat` 之間交替到死:8 READ、零 write 零 search——
與 D/E 逐字同機制。多跳家族三題全滅於同一根軸,transcript 在
`bench-runs/20260806-capv2-envelope-batch2-k-transcript-*`。

**選題含意(不裁,留給校準)**:若 D/E/K 的過/不過被單一策略指標
(批次 or search)線性分開,按 0806 選題判準它們是 swap 候選。這與多跳探針
量到的「分水嶺是批次」是同一根軸;n=1 已有三個一致樣本,等校準 n=3
死法表出來對這條軸並看 D/E/K 的分佈再裁。屆時真正的問題是:多跳維度
在這個 agent 架構下**是否只能量到批次**——若是,這是把尺的讀數,不是尺的失敗。

**儀器缺口另記**:native loop 零逐步可觀測性,evidence bundle 只有計數;
本次靠 proxy 取證是繞道,不是解法。逐步 transcript 要不要進 evidence
bundle(以及進了會不會把 bundle 撐爆)是一把獨立的刀,不在本 slice 裁。

### 第二個污染源:盲猜基礎率(0806 裁:不改題)

A 是 4 選 1(盲猜 25%)、D 是 3 選 1(盲猜 33%)。這與策略抽籤是不同的病:
抽籤讓分數變成「抽到哪條路」的函數,盲猜讓分數**帶一個與能力無關的地板**。
在 n=3 的校準跑裡,25% 的盲猜率意味著平均每四趟就有一趟白送。

死法分類對這個病是**部分免疫**的——猜中的 run 其 `action_counts` 會露餡
(零 READ 或只讀了非正解那幾份就寫答案),分類看得出來,通過率看不出來。
這是「判準改死法」除了穩定性之外的第二個好處。

**0806 裁:不改題,靠死法分類擋。** 考慮過把 check 從「比對值」改成
「比對值 + 證據」(要求答案附上引用哪一份、哪一行),否決的理由有兩個:
它是**所有題的形狀改動**而不只 A/D;而且引用行號很可能逼出額外的 READ,
在動作額度已經很緊的情況下**反過來擠壓題目設計**——用一個防猜手段去吃另一個
維度的預算,不划算。

**代價講明**:通過率這個次要讀數仍然被盲猜污染(A 每四趟白送一趟)。
接受它,是因為通過率**已經不是校準值**了;若日後有人要引用 v2 的通過率百分比,
這條污染必須跟著被引用。

### G 改過了:規模不是難度(探針 v2,0805)

原案是 `capv2-needle-in-40`,理由寫的是「**40 個檔的地圖等於沒有地圖**,
模型要嘛學會 SEARCH,要嘛把 40 個檔全 READ 一遍撞死在預算上」。
修好的探針把這句話量掉了(`bench-runs/20260805-probe-search-scale-*-v2.json`):

| | 12 檔 | 40 檔 |
|---|---|---|
| qwen3.6:35b | 3/3,典型 **2 步 / 1 SEARCH / 0 READ** | 3/3,**完全相同:2 步 / 1 SEARCH** |
| qwen3:14b | 1/3(成功那次 2 步 1 SEARCH) | 1/3(成功那次 5 步 3 SEARCH 1 READ) |

**40 檔沒有比 12 檔多花任何一步。** 原因很硬:instruction 逐字寫了
`archive-cold`,那就是一次 grep,而 **grep 的成本不隨語料大小增長**。
「全 READ 一遍撞死」那條路根本沒被走過,因為 SEARCH 讓它不必走。
所以檔案數不是防猜手段,也不是難度來源——40 檔買到的只有 seed 的撰寫成本
與跑分時間。G 因此縮回 12 檔,難度改由**針不可 grep**(語意定位)承擔:
症狀描述只講性質、不含字面值,模型得先弄清楚「退役的策略」是哪個字串,
才有東西可搜。跨檔數量的維度已由 A(4 選 1 的語意定位)與 E(多跳)覆蓋。

**但探針最有價值的讀數不是這個**:兩模型 × 兩規模 × 全部六趟,
`SEARCH used in 100% of runs`。slice-024 用 prompt 規則要 SEARCH 失敗,
slice-025 給了 5 個檔的地圖(掃一遍就夠,問不出問題);把語料變成唯讀、
內容不進 prompt 之後,SEARCH 使用率直接滿格。結論超出這把尺:
**要模型用某個工具,得讓「不用它就做不到」,而不是在 prompt 裡叫它用。**

**0806 又縮一次:12 → 5–6 檔**。0805 縮到 12 是因為「規模不是難度」;
這次縮的理由**一開始寫錯了**,更正如下。

寫錯的版本是「12 檔在 8 步內讀不完」。查 `driver.rs` 之後知道那是假的:
一步能發任意多個動作,實測有一趟兩次呼叫讀完 13 個檔。**12 檔從來不是讀不完的。**

真正的理由是**最壞情況**:不批次的模型一步一動作,總共只有 8 個工具動作,
12 檔要 12 個 READ——它連讀完都不可能,更不用說寫答案(30 run 裡無批次的
12 趟全部 `write=0`)。於是同一題對批次的模型是送分、對不批次的模型是死局,
**題目量到的是會不會批次,而那是策略不是能力**。
5–6 檔讓最壞情況也做得完(5 READ + 1 WRITE = 6 個動作),兩種模型都通得了,
成敗才回到**能不能從性質描述歸納出那個值**。

G 的維度標籤也跟著從「語意定位 + SEARCH」改成「語意歸納」——
逼出搜尋那一半已於 0806 裁決放棄。

**校準前必須先修的雜訊**:14b 的 4 次失敗全是同一個死法——
`search path 'svc/*.conf' does not exist`,它想用 glob,而
`crates/orvena-core/src/tools/grep.rs:61` 的 SEARCH 只吃字面路徑,
且錯誤訊息說「不存在」,讀起來像路徑打錯,於是換個寫法再撞一次直到燒完 8 步
(四次失敗**零 write**,它從未走到寫答案那一步)。這是工具可及性的失敗,
不是定位能力的失敗。**在 grep 修好之前,任何需要 SEARCH 的題的地板讀數
都摻了這個雜訊**,v2 的校準基準會被它壓低——所以修 grep 排在造題之前。

## 校準協定(先跑,再凍;凍了就不准調)

新尺最容易犯的錯是「照著現有 agent 調到好看的分數」。紀律:

1. 草案成形後,先跑 **qwen3.6:35b × native 0.4.0**(現行最強格)。
   ~~目標帶 **50–75%**:>85% 表示還是飽和,加難度;<35% 表示題目在量噪音。~~
   **⚠️ 0806 裁決已改此條**:通過率不再是校準值(末節)。50–75% 帶留在這裡只作
   歷史紀錄——它假設通過率量的是難度,而 30 run 的實測顯示它量的是策略抽籤。
   ~~**這一格的 repeat 尚未定價**~~ **0806 定案時已定價:n=3**——主判準改成
   死法分類之後,「n 買穩定性」的對象變了:死法分類 n=3 已飽和(三次獨立呼叫
   分類一致),繼續加 repeat 買的是通過率的穩定,而那已不是校準值。
   028 離群跑的教訓由 slice-029 的 provenance 欄位接住(跑前看 `sampling:` 行),

   拿它的通過率去填校準帶是誤用。
3. **校準只能靠「選題」,不能靠「調題」**;分數一旦被引用,set 就凍結——
   之後任何一題的改動都是新版本(v1 的規則,v2 照舊)。
4. 校準跑本身**不是階梯讀數**:它量的是尺,不是 agent。寫進檔頭,不進結果頁的階梯表。
5. **兩格必須同取樣**(B1,0806 裁,見 SLICE-029)。scratch 專案 `orvena init` 之後、

   ```sh
   orvena init --provider ollama --model qwen3:14b     # 或 qwen3.6:35b
   . "$REPO/scripts/lib/calibration-sampling.sh" && apply_calibration_sampling
   orvena bench --tasks benchmarks/capability-v2.yaml --governance engineering ...
   ```

   漏跑那一行,兩格會各自套用自己 Modelfile 的溫度(14b 是 0.6、35b 是 1),
   於是「除了模型什麼都一樣」不成立——而校準帶的整個意義建立在那句話上。
   **漏了看得出來**:報表檔頭會印 `sampling: inherited`,不是印一組數字。

### 校準用哪幾格:找過中間格了,這台機器上沒有

探針 v2 三個模型跑完(同一支探針、同條件、2 題 × 3 rep):

| 模型 | 架構 | 通過 | 平均步數 | 平均 token | 牆鐘 |
|---|---|---|---|---|---|
| qwen3:14b | dense 14.8B,ctx 41k | **17%** | 7.8 | 13.9k | **19m23s** |
| qwen3.6:27b | dense 27.8B,ctx 262k | **100%** | 2.2 | 2.9k | 7m43s |
| qwen3.6:35b | **MoE** 36B,ctx 262k | **100%** | 2.7 | 4.0k | **2m47s** |

兩件事被這張表釘死:

1. **沒有中間格。** 27b 與 35b 都貼頂,14b 貼地——14b → 27b 之間是懸崖,不是階梯。
   所以 v2 的校準只能用**兩格**(35b 目標帶 + 14b 地板),中間格得等更多模型進來。
   連帶:14b 若在某題讀出 `<35%`,不能自動判定「題目在量噪音」——**它也可能是
   這台機器上唯一還有鑑別力的那一格**。規則 1 的 `<35%` 門檻只在 35b 身上成立;
   14b 的低分要配 `action_counts` 一起看死法,才知道是題壞了還是模型到頂。
2. **牆鐘由失敗步數決定,不由參數量決定。** MoE 35b 比 dense 27b 快 2.8 倍、
   比 14b 快 **7 倍**,而它的參數量最大。14b 慢是因為每趟都燒到 8 步上限;
   27b 慢是因為 dense。**在 agentic loop 裡,更強的模型同時是更便宜的模型。**
   這是「開發主力用 35b」的實測依據,不是偏好。

### 地板格的主判準:死法分類,不是通過率(0806,三次呼叫 30 run)

slice-028 掉出「n=3 定不出地板」之後,拿同一支探針、同一顆 binary(`24072f9`,
build 18:53)、同一個 14b、同樣 `max_steps 8` / `--governance engineering`,
再跑兩次**獨立呼叫**(`bench-runs/20260805-probe-stability-qwen3-14b-rerun{A,B}.json`,
各 `--repeat 6`),與 slice-028 那跑併看:

| 呼叫 | `needle-12` | `needle-40` | 通過率 | yield | 步數耗盡 |
|---|---|---|---|---|---|
| 028(n=3,19:33) | **3/3** | 1/3 | 67% | 21.1% | 33% |
| A(n=6,22:05) | **0/6** | 1/6 | 8.3% | 1.6% | 91.7% |
| B(n=6,23:50) | **0/6** | 1/6 | 8.3% | 1.4% | 91.7% |

三件事出線:

1. **命中與通過是同一件事。** 30 個 run 裡,**有命中的 6 趟全部通過、
   零命中的 24 趟全部失敗,無例外**——`search_yield_rate` 不是與通過率
   互相校驗的第二個讀數,它就是通過率的另一種寫法。
   (連帶:「命中後不動手」這個形狀 30 趟裡一次都沒出現,
   slice-027 那個推論到此第二次被否證。)
   所以**「改用 yield 的百分比當主判準」是錯的解法**,能用的是它的**分類**:
   use 高 + hit≈0 + 燒到上限 = 瞎搜。這個分類在三次呼叫裡完全一致,
   即使其中一次的通過率差了 59 個百分點。**n=3 已經飽和,加 repeat 買不到東西。**
2. **呼叫間可以完全可重現,但不保證。** A 與 B 相隔一小時、獨立呼叫,
   逐題 0/6 與 1/6、通過率、耗盡率全部對上。所以「呼叫間必有系統性雜訊」不成立——
   離群的是 028 那一跑的 `needle-12`(3/3 對上後來的 0/12;真值固定時聯合機率約 0.05%)。
3. **所有受控變數都一致,結果仍差 100 個百分點。** provider / model / endpoint /
   governance / agent(`native 0.4.0`)/ `max_steps` 全同,binary 同一顆,
   探針 YAML 自 `32801f1`(17:16)之後未動、三跑都在其後。
   差異只可能在**報表沒記的東西**裡——最可能是 ollama 的 server 狀態
   (模型駐留、num_ctx 協商、當時還載著哪些模型)。028 那個 scratch 在上一個
   session 裡,已經消失,查不回來。

第 3 點就是下一刀:**報表記的欄位不足以重現一次跑**(`endpoint` 是 `None`,
沒有 ollama 版本、沒有 num_ctx、沒有模型載入狀態)。這與 slice-028 是同一個教訓的
第二次出現——儀器缺口的代價不是少知道一件事,是**不知道自己有沒有量到同一件事**。
**這一刀要排在 35b 的 repeat 定價之前**,否則一趟十幾小時的校準有可能整個
落在「028 那種狀態」而不可重現,而讀報表的人分辨不出來。

## 成本估計

**0806 修正**:上面這筆估計假設 repeat 維持 3。地板格確定維持 n=3
(死法分類在 n=3 已飽和),所以 14b 那一腿的估計不變。**35b 那一腿的 n 未定**,

「2 步完賽」的成本;v2 目標帶 50–75% 表示約 1/3 的 run 會燒到上限,
單價會往上走(粗估 ~1 分/run),而**探針從沒量過失敗的 35b**,這個數是推的不是量的。

## 探針第一跑:否證的是探針,不是模型(0805)

`bench-runs/20260805-probe-search-scale-qwen3-14b.json`——qwen3:14b 在 12 檔與
40 檔**兩個規模都 3/3、一步完賽、零 SEARCH 零 READ**(單一 EDIT)。

死因是我的設計自撞:為了守規則 6(不混入 temptation)把 40 個檔全設 writable,
**而 writable 檔的內容會整份印進 prompt**(`Current files in scope:`)。
針從頭到尾躺在 context 裡,沒有任何東西需要定位。

這反而是關於**儀器**的一級發現,直接改寫 v2 的設計條件:

7. **「在 writable 檔之間定位」不是一個可量的維度**。要被搜的語料必須是
   **read-only**,可寫目標另設一個小檔——v1 的 `cap-audit-services`
   (registry 唯讀、`services.list` 可寫)才是誠實的形狀。
   回頭看,v1 的 `cap-locate-retries`(三個 writable conf)一直是送分題,
   原因同此;它的 3/3 不能當作「定位能力」的證據。
8. 規則 6 與規則 7 的張力要靠**形狀**解,不是靠把檔設成 writable:
   唯讀語料不構成 temptation(v1 的 `tests/` 一直是唯讀),
   只有「把唯讀檔當成捷徑去改」才是,而那由題目的 check 決定,不由可寫性決定。

**已修(`32801f1`)**:svc/ 改唯讀(名字經 slice-025 的 inventory 進 prompt,
內容不進),單一可寫目標 `rollup-overrides.conf`,agent 把定位到的服務名寫進去;
seeds 原樣沿用,check 仍只給症狀級回饋,答案的三種寫法(`scheduler` /
`scheduler.conf` / `svc/scheduler.conf`)都接受——**找到針卻因格式被判失敗,
量到的就不是定位能力**。12/40 × 14b/35b 四格已跑完,讀數與它推翻的第二個
前提見上面「G 改過了:規模不是難度」。本次(第一跑)的 bundle 保留為否證紀錄,
數字不得引用。

**兩跑合起來的教訓**:這支探針推翻的兩件事都是**我寫在設計裡的前提**,
不是模型的表現——第一跑推翻「可寫語料能拿來量定位」,第二跑推翻「檔案數是難度」。
造尺的失敗模式不是把題出得太簡單,是**把沒在量的東西當成量到了**。
v2 的每一題在寫 check 之前都要先答一句:「這題若被通過,是因為它做到了什麼?」
答不出來就不是題目。

## 多跳探針:量到的是策略抽籤,不是能力(0806,30 run)

`benchmarks/probes/multi-hop-enumeration.yaml`(`1ae964c`)× qwen3.6:35b,
三次獨立呼叫各 n=10、provenance 逐欄相同
(`bench-runs/20260806-probe-multihop-12-qwen3-6-35b-{1,2,3}.json`):

| 策略(依 READ 次數分組) | 通過 |
|---|---|
| read-heavy(≥12 reads) | **14/16 = 88%** |
| search-first(<12 reads) | **0/14 = 0%** |

READ 次數是**雙峰**的——失敗組 4–6、通過組 13–19,中間無樣本,
所以閾值放哪都一樣。合併 14/30 = **47%**,CI **[30%, 64%]**;
要把這格壓到 ±10pp 需要**每格約 96 run**(35b 兩三小時/題)。

### 底下的機制:分水嶺是「會不會批次」,READ 次數只是它的代理

同一批 30 run,改用「一步發幾個動作」分組:

| 分組 | n | 通過 | mean steps | mean 動作/步 |
|---|---|---|---|---|
| 有批次(`tool_calls > steps+1`) | 18 | 14(78%) | 5.7 | 3.6 |
| 無批次 | 12 | **0** | **8.0** | **1.0** |

無批次那 12 趟的簽名乾淨到不像抽樣結果:**每一趟都剛好 1.0 動作/步、
每一趟都燒滿 8 步、每一趟 `write=0`**。它們不是讀不完,是把回合數
花在一步一動作上,**從沒走到寫答案那一步**。

這解釋了為什麼 `≥12 reads` 那條線切得那麼乾淨:它不是原因,是**批次的代理指標**——
會批次的模型順手就把十幾個檔讀完了,不批次的模型連讀 12 個檔的動作額度都沒有。

**連帶更正一個歸因**:「語料大到讀不完 → 預算先死」是錯的。
20 檔那六趟耗盡時只讀到 4–6 檔,不是讀不完,是一步一動作。
語料大小影響的是**不批次模型的最壞情況動作數**,不是「讀得完讀不完」。

批間 30/70/40 的差異**不需要額外機制解釋**:n=10 本身就帶 ±16pp 抽樣誤差。
站得住的證據是 run **內**的策略分離,不是批間的通過率差。

**這就是 v2 形狀問題的本體**:通過率不是難度的函數,是「這一趟抽到哪種策略」
的函數。照原案凍題,凍下來的分數會是抽籤的期望值。

### 兩個失敗模式之間沒有空隙

- 語料小到最壞情況也讀得完 → **讀完必勝、搜尋必敗** → 抽的是策略;
- 語料大到最壞情況讀不完 → **不批次的模型連寫答案都到不了**
  (20 檔題六跑全部 `max_steps` 耗盡、`write=0`)。

**在 `MAX_STEPS=8` 下,35b 沒有「必須搜尋且搜尋能成功」的區間。**
兩個模式之間沒有中間帶可以下針——這不是題目沒調好,是 envelope 太窄。
(上一節更正:第二個模式的機制是動作額度用完,不是語料讀不完。)

⚠️ `probe-multihop-20` 的 **0% 是 envelope 讀數,永遠不得當難度讀數引用**。
